# UESTC_DeskFriend 架构哲学：器官化设计（各司其职）

> 指导文件：开发任何新功能前先读本文档，按「代码归属判定」确定代码放哪层。
> 原则来源：顶级 Agent 框架的共性——**大模型不碰物理硬件，器官不懂大模型，
> 主控中心编排一切**。2026-08-11 定稿（Mouth 器官重构时确立）。

## 一、核心原则（一句话）

> 大脑只做一件事：输出意图（文本 / 工具调用）。真正执行动作的，是外面的主控中心。
> 器官只做一件事：物理输入输出 + 本地信号处理，然后像广播一样发射事件。
> 主控中心提前监听器官信号，用自己内部的 LLM 方法做门卫判定和回复编排。

**推导出的硬规则**：
1. **LLM 绝不直接碰物理硬件**——不能由模型代码直接开麦克风、放声音、截屏；
   模型只输出"想说的话/想做的事"，执行由主控中心完成。
2. **器官不知道大模型存在**——器官代码里禁止 import brain / 调 LLM；
   器官拿到的输入永远是命令或数据，输出永远是信号或状态。
3. **主控中心（spine，脊髓）是唯一的编排者**——所有跨器官的流程（收到语音→判定→回复→
   说话→被打断→注入上下文）都在 spine 组装，器官之间不互相调业务流程。

## 二、三层模型与当前器官地图

```
                 ┌── 大脑（LLM）──────────────────────────┐
                 │ brain.py 门面 → backends/               │
                 │ 只输出 BackendResponse(回复文本/工具调用) │
                 └──────────────┬─────────────────────────┘
                                │ 回复/判定结果
┌───────────────────────────────┴──────────────────────────┐
│              主控中心：spine.py（Spine，脊髓）              │
│  监听器官信号 → should_reply 门卫 → 编排回复 → 命令器官     │
│  打断位置注入（mouth.interrupt 前缀 → brain 上下文）        │
└──┬────────────┬────────────┬────────────┬────────────────┘
   │ 信号        │ 信号        │ 命令        │ 命令+信号
   ▼            ▼            ▼            ▼
 ear: listen.py   eye: vision.py  mouth: mouth.py  skin: skin.py
 VAD+Whisper→text 截屏理解       发声+回声门控    贴图/气泡/动画/触摸
 text_signal(str)                finished 信号    ←show_bubble/set_anim_state
                                                  →text_submitted/touched
```

| 器官 | 文件 | 职责（只管这些） | 对外接口 | 事件广播 |
|------|------|------------------|----------|----------|
| 耳 | `listen.py` | 采集 → VAD → Whisper 转写；句间窗口门控 | `text_signal(str)` | 转写结果、`interrupt_requested`（窗口内用户说话） |
| 嘴 | `mouth.py` | 发声 + 门控 + 句间监听窗口（内部消化尾巴/try-finally/guard） | `speak(text)` / `interrupt()->前缀` / `busy` / `speaking` / `window_open` | `finished` |
| 眼 | `vision.py` | 截屏（多后端回退） | `look_at_screen()` | — |
| 皮 | `skin.py` | 显示（贴图/气泡/动画）+ 触摸输入（点击/拖动/双击/文字） | `show_bubble(text)` / `hide_bubble()` / `set_anim_state(state)` | `text_submitted(str)`、`touched` |
| 脑 | `brain.py` + `backends/` | 只产回复意图；门卫判定（judger） | `get_llm_response` / `get_response_with_context` | — |

**器官间唯一允许的依赖**：单向、只读状态。例：耳读 `mouth.speaking` 与
`mouth.window_open`（嘴在发声时麦克风拾到的是回声 → 耳只在句间监听窗口拾音）。
这是物理层协同，不是业务流程耦合。

## 三、大脑只输出意图（含工具调用）

- 大脑的输出 = 文本 或 工具调用意图（如 `look_at_screen`）。
- **工具调用由主控中心执行**（`spine.tool_executer`），执行结果作为上下文回喂大脑。
- 大脑不持有任何"如何截屏/如何播放"的知识，正如它不该知道"怎么动嘴唇"。

## 四、代码归属判定（写新功能前逐条过）

新增一段逻辑时，按顺序回答：

1. **它操作物理硬件或本地信号吗？**（麦克风、扬声器、屏幕、传感器）
   → **器官**（新建器官文件或扩展现有器官）。器官负责：采集/输出 + 本地处理 + 信号广播。
2. **它决定"回不回 / 回什么"吗？**（should_reply、prompt 组装、记忆、人格）
   → **大脑侧**（`brain.py` / `backends/`），输出意图即可。
3. **它是跨器官的流程编排吗？**（信号到达后怎么走完整个回合）
   → **主控中心 spine**：监听信号 → 判定 → 命令器官 → 处理结果。
4. **它是器官的内部生命周期细节吗？**（如门控置位/释放、超时、异常清理）
   → **器官内部消化**，对外只暴露稳定接口。例：门控置位/余响尾巴住在
   Mouth 内部而不是主控（曾犯过的错：`_speak_then_release` 住在 ui.py，
   2026-08-13 已随 ui.py → skin+spine 拆分根除，见 §五）。
5. **器官需要知道别的器官的状态吗？** → 只允许单向只读（注入引用，读状态属性），
   禁止器官互调业务流程、禁止双向依赖。

## 五、反模式（这些发生过或容易发生，禁止）

| 反模式 | 为什么错 | 正确做法 |
|--------|----------|----------|
| 器官里 import brain / 调 LLM | 器官不再纯粹，无法独立测试和复用 | 器官只发信号；判定/回复由主控中心做 |
| 主控里堆器官实现细节（门控置位、尾巴、生命周期） | 主控变成大杂烩，器官没有自我边界 | 细节收进器官，主控只编排 |
| 器官之间互相调业务方法 | 耦合，改动互相牵制 | 单向只读状态注入（如 listen.mouth） |
| 大脑输出物理操作细节 | 换硬件/换实现时大脑也要改 | 大脑只输出意图，执行在主控中心 |
| 为"省事"让器官直接吞掉信号不发广播 | 主控中心无法介入，无法扩展 | 器官永远广播事件，主控中心决定用不用 |

## 六、新功能开发走查示例

- **新感官**（如"触摸检测"）：新建 `touch.py` 器官（采集→信号），spine 监听信号编排。
  器官文件里只有物理层逻辑 + 信号；判定"要不要回应"去 brain/judger。
- **新回复能力**（如流式回复）：改大脑侧（`backends/`）输出形态；
  主控中心收到新形态后编排展示/朗读。
- **新发声行为**（如哼歌/音效）：扩展 `mouth.py`（器官内部消化，接口不变）。
- **新交互流程**（如"触碰→撒娇动画→说话"）：全部在 spine 编排，器官只被命令。

## 七、评审检查清单

新代码过审时对照：
- [ ] 器官代码无 brain/LLM 依赖？
- [ ] spine 只做编排，没有器官实现细节？
- [ ] 器官间依赖单向且只读？
- [ ] 大脑侧没有物理操作代码？
- [ ] 事件走信号广播，主控中心可介入？
